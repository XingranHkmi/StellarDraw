## 1. 项目背景与目标

### 1.1 项目背景

教师在课堂上需要随机抽取学生回答问题、上台演示或分组。传统做法（点名册随手一指、按学号顺序、第三方网页抽号工具）存在三个痛点：

1. **公平性存疑**：随手指定容易被学生质疑"老师是不是故意的"，缺乏随机性的可视化证明。
2. **重复率不可控**：完全随机可能连续抽到同一人，也可能一节课下来半数学生从未被抽到。
3. **课堂气氛平淡**：抽号环节本可以是课堂节奏的"提神点"，但现有工具界面枯燥，无法调动学生注意力。

同时，年轻教师群体对二次元/抽卡游戏文化有较高的接受度和偏好，一个具备"抽卡仪式感"的抽号工具能够显著提升课堂互动意愿——**前提是这份仪式感不能以牺牲课堂节奏为代价**。

### 1.2 核心矛盾：氛围感 vs 课堂效率

这是本项目贯穿始终的设计主线：

| | 氛围感诉求 | 效率诉求 |
|---|---|---|
| 表现形式 | 卡牌滑出、3D 翻转、看板娘、光效粒子、音效 | 3 秒内出结果、零学习成本、不出意外 |
| 设计对策 | 全部动画耗时控制在 **1.2 秒内可跳过/可加速**，且提供一键退路 | — |
| 兜底机制 | — | **「简洁视图」按钮**：一键启动一个朴实无华的外部抽号器，彻底剥离所有装饰 |

**设计原则：装饰永远不拦截操作路径。** 学生看氛围，老师看速度。

### 1.3 产品目标

| 编号 | 目标 | 可衡量指标 |
|---|---|---|
| G-01 | 抽出结果的速度不慢于传统点名 | 从点击"抽取"到看见姓名 ≤ 3 秒（含动画） |
| G-02 | 保证课堂抽取的公平性与覆盖率 | 去重模式下，一轮内全班每人最多被抽中 1 次 |
| G-03 | 提供了课堂仪式感 | 抽卡全流程动画完整、无掉帧 |
| G-04 | 零学习成本 | 新用户首次打开，不做任何配置即可完成一次抽取（详见 E-01 的空名单引导） |
| G-05 | 部署零门槛 | 单个 exe 双击即用，无需安装 Python 或任何运行时 |

### 1.4 非目标（明确不做）

为避免范围蔓延，以下内容**不在本期范围内**：

- ❌ 学生端联动（学生用手机扫码查看结果）
- ❌ 云端同步、账号体系、多设备数据同步
- ❌ 课堂积分/评价/考勤统计等教务功能
- ❌ 抽号结果的持久化历史报表与导出（已确认：仅显示最近几条，不落盘）
- ❌ macOS / Linux 移植
- ❌ 联网功能（本软件**完全离线运行**）
- ❌ Excel（`.xlsx`）格式支持（已确认：**只做 CSV**，见 TBD-04）

## 2. 需求确认记录（决策溯源）

以下结论均来自与用户的逐项确认，是本 PRD 的立论基础。

### 第一轮确认（2026-09-12）

| 议题 | 结论 | 影响 |
|---|---|---|
| 学生名单来源 | **手动录入 + 导入名单文件两者都要** | 需要名单 CRUD 界面 + 文件解析 + 多班级档案 |
| 抽取去重规则 | **界面提供开关，老师自行切换** | 抽取引擎需支持两种模式，且开关状态需可保存 |
| "抽取 5 次"表现 | **5 张卡同时滑出，点哪张翻哪张**（未点的保持卡背） | 需支持卡牌独立状态机，不能做"全部自动翻开" |
| 简洁视图实现 | **启动另一个独立 exe** | 主程序只负责"启动外部程序"，不与之共享任何状态 |

### 第二轮确认（2026-09-12）

| 议题 | 结论 | 影响 |
|---|---|---|
| 主程序与极简 exe 的关系 | **两者完全独立，与主程序无任何关系，可以是任意普通 exe** | 「简洁视图」退化为一个**通用的外部程序启动器**，不需要做进程间通信 |
| 看板娘素材 | **先用占位图，预留替换目录** | 需定义 assets 目录规范与替换说明 |
| 音效 | **要音效，默认开启** | 需实现音效播放 + 一键静音 |
| 抽取记录保存 | **只显示最近几条，不保存**（关软件即清空） | 不做落盘，去重状态仅存内存 |

### 第三轮确认（2026-09-12）

| 议题 | 结论 | 影响 |
|---|---|---|
| 外置程序路径指定方式 | **界面上自己选 exe 路径**（设置面板内提供文件选择器，路径自动记住） | 需文件选择器 + 配置持久化 |
| 名单管理入口 | **独立的设置面板**（主界面保持干净） | 主界面不放名单侧栏 |
| 教室屏幕分辨率 | **3840×2160（4K）** | ⚠️ 最高优先级性能约束，见 §7.1 |
| 卡牌区形态 | **叠放的牌堆**，抽卡时最上面那张飞出 | 需实现牌堆视觉 + 顶部卡片位移动画 |
| 技术栈 | **方案 A：Python + Pywebview(WebView2) + HTML/CSS/JS** | 见 §9 |
| 视觉风格 | **明亮二次元手游风**（参考《崩坏：星穹铁道》的配色基调，但不局限于此） | 决定配色与素材方向 |
| 抽取模式 | **仅"抽取 1 次"和"抽取 5 次"** | 不做自定义 N 次、不做"全班抽完" |
| 主窗口形态 | **普通窗口**（带标题栏，16:9 锁比） | 布局需适配可调整尺寸的窗口 |

**主要用户：小林老师，26 岁，高中英语教师**

- 有 6 年教龄，教一个班，约 35 人
- 每天至少使用抽号工具 5 次（课堂提问）

**区块职责**

| 区块 | 位置 | 职责 | 优先级 |

| 简洁视图按钮 | 左下（设置入口右侧） | 启动用户指定的外部 exe | P0 |
| 抽取按钮组 | 右下 | 「抽取 1 次」「抽取 5 次」 | P0 |

> **布局说明**：左下角集中放置"设置 / 一键静音 / 简洁视图"三个低频/工具型入口，与右下角的"抽取"主操作区分开，避免误触。设置入口使用齿轮图标 + 文字标签，触摸目标 ≥ 44×44px。
>
> **优先级口径修正（TI-19 / TI-20）**：上表把「卡牌区、加载图标、看板娘」列为 P1，但 §8.1 的 P0 验收项 AC-05 / AC-06 已明确要求「卡牌滑出 + 点击 3D 翻转」，且抽取时序（§6.1）也用到加载图标与看板娘。二者冲突时**以验收标准为准**，因此 P0 阶段：
> - **卡牌区（简洁牌堆）、加载图标（静止／旋转两态）、卡牌滑出与 3D 翻转**：全部实现；
> - **牌堆多层视觉打磨、看板娘三态切换与呼吸/眨眼动效**：留到 P1，P0 仅加载待机态并受开关控制。

| 窗口默认尺寸 | **2560×1440（物理像素）**（已确认，理由见下；开窗前按系统 DPI 缩放折算为逻辑尺寸，见 TI-32） |
| 宽高比 | 锁定 16:9，拖拽缩放时保持比例 |
| 窗口形态 | 普通窗口（带标题栏），支持最小化/最大化/关闭 |
| 最小可用尺寸 | 1280×720（**逻辑像素**；小于此尺寸时布局按比例缩放而非重排） |
| 窗口位置 | 启动时在**主显示器工作区**（已扣除任务栏）内居中，保证窗口完整可见（TI-32） |
| 系统缩放适配 | 尺寸按**物理像素**表达并按系统 DPI 折算；屏幕放不下时按工作区的 92% 上限收缩（TI-32） |
| 布局单位 | 全部使用相对单位（`%` / `vw` / `vh` / `clamp()` / `rem`），**禁止硬编码 px 定位** |
| 高 DPI | 必须在 4K（200% 缩放）下文字锐利、无错位、无模糊位图 |

**关于 2560×1440 的技术复核结论（AI 意见）**

用户在 TBD-03 中提出将默认窗口从 1920×1080 改为 2560×1440，并要求 AI 若认为 1920×1080 更优则直接反驳。**复核结论：采纳 2560×1440。** 理由：

1. **教学场景优先级**：「看得清」的优先级高于「省一点填充率」。1920×1080 的窗口在 55–75 寸的 4K 一体机上仅占屏幕面积约 25%，投影到教室后排时学生姓名可读性不足；2560×1440 占约 44%，视野显著改善。
2. **性能差距在可控范围内**：2560×1440 的像素量为 3.69M，是 1920×1080（2.07M）的 1.78 倍。但在 §7.1 已强制约束「动画只使用 `transform` 与 `opacity`」的前提下，卡牌动画由 GPU 合成器搬运纹理完成，开销取决于**合成层数量与图层面积**，而非逐像素重绘。Intel UHD 级别核显处理 3.69M 像素的图层合成属于常规负载。
3. **真正的性能杀手已被排除**：模糊、大面积阴影、`border-radius` 动画、实时滤镜——这些 CPU 密集操作才是无独显机器掉帧的根因，PRD 已通过 NFR-P7 / NFR-P12 明令禁止。
4. **像素对齐（2026-09-24 修订，TI-32）**：4K 屏常用 150% 系统缩放 → 其**逻辑**分辨率为 2560×1440，而面板的**物理**像素是 3840×2160。**2560×1440 是物理像素目标**：窗口物理尺寸落在 2560×1440 时正好占屏约 44%，且 1 个 CSS px 对应 1 个物理像素 —— 文字最锐利、观感与设计稿一致。因此开窗前必须先把设计值按系统 DPI 折算成逻辑尺寸（4K@150% → 逻辑 1707×960）再交给 pywebview；否则 pywebview 会再乘一次缩放，把窗口撑成 3840×2160（整屏），既不符合"占屏约 44%"的意图，也会让居中计算失准。

**但保留一条退路**：若在真实教室机器上实测帧率不达标（AC-17），**第一个应当调整的旋钮就是窗口默认尺寸**（回退至 1920×1080），而非削减动画内容。此对策已写入 R-01。

```
[老师点击"抽取1次"]

   ├─ 1. 按钮立即进入禁用态，加载图标开始旋转，看板娘切换"抽取中"态

   │

   │
   ├─ 4. 卡片进入"待翻开"态（轻微呼吸/悬浮提示，暗示可点击）
   │
   ├─ 5. [老师点击卡背]
   │      ├─ Y 轴 3D 翻转 180°（约 600ms）（**点击卡背不单独配音效**，见 TI-28）

   │      │      第 1 行 = 学号（小字号，如 "07"）
```

### 6.2 五次抽取完整时序

1. 点击"抽取 5 次"后，Python 一次性计算 5 名不重复学生（去重开启时）
2. 5 张卡牌**同时**从牌堆滑出，在中央区域**横向排列**（间距均匀，带轻微错落角度更佳）
3. 每张卡牌**独立**存在"卡背 / 已翻开"两种状态
4. **老师点哪张，哪张才翻**。未点击的保持卡背，可以一直不点
5. 已翻开的卡牌可保持展示，直到老师进行下一次抽取
6. 下一次点击"抽取"按钮时，**上一轮所有卡牌（含未翻开的）自动淡出消失**，重新开始
7. 每张已翻开的卡牌正面均按 F-08 的规格显示学号与姓名两行。**5 张卡并排时字号自动降档**，确保不换行、不溢出

### 6.5 CSV 名单文件规范

**模板内容**（`data/roster_template.csv`）：

```csv
Num,Name
```

**编码要求**：**UTF-8 with BOM（`utf-8-sig`）**。

> 为什么必须带 BOM：Windows 版的 Excel 双击打开无 BOM 的 UTF-8 CSV 文件时，会按 GBK 解析，导致中文姓名乱码。带 BOM 可让 Excel 正确识别编码。这是本项目中一个必须严格遵守的实现细节。

**导入时的编码嗅探顺序**：`utf-8-sig` → `utf-8` → `gbk`，任一成功即采用。

**字段规则**

| 字段 | 必填 | 说明 |
|---|---|---|
| `Num` | 否 | 学号。可留空；留空时结果卡不显示学号行 |
| `Name` | 是 | 姓名。为空的行整行跳过 |

**导入行为**

- 首行若识别为表头（`Num` / `Name` 的各种大小写，或中文"学号""姓名"），则跳过
- 逐行读取，过滤全空行
- 导入前校验文件可解析性；解析失败时给出明确错误，**不修改现有名单**（见 E-08）
- **导入冲突处理（TI-11 已确认）**：若当前班级已有名单，弹出选择框，让老师明确选择「覆盖当前班级」或「追加到当前班级」，**不做静默覆盖**，避免误操作造成数据丢失

## 7. 非功能需求

### 7.1 性能需求 ⚠️ 最高优先级

**运行环境基线**：Intel i5-12500H · **睿频被禁用**（性能约为标准 12500H 的 60–70%）· 无独立显卡 · 4K（3840×2160）屏幕 · Windows 希沃一体机。默认窗口 2560×1440。

> **关键判断**：4K 全屏的像素填充量是 1080P 的 **4 倍**；默认窗口 2560×1440 的像素量是 1080P 的 **1.78 倍**。在无独显且睿频受限的机器上，这是本项目最大的技术风险。所有视觉设计必须为性能让步。

| 编号 | 指标 | 目标值 | 测量方式 |
|---|---|---|---|
| NFR-P1 | 动画帧率 | **≥ 50 FPS**（目标 60 FPS），不允许出现肉眼可见卡顿 | 浏览器 DevTools Performance 面板录制 |
| NFR-P2 | 冷启动时间 | 从双击 exe 到窗口可交互 **≤ 3 秒** | 秒表 / 日志埋点 |
| NFR-P3 | 抽取响应延迟 | 点击抽取到卡牌开始运动 **≤ 100ms** | 页面埋点 |
| NFR-P4 | 内存占用 | 峰值 **≤ 300MB** | 任务管理器 |
| NFR-P5 | 长时间运行 | 连续运行 2 小时（约 60 次抽取）无内存泄漏、无帧率衰减 | 压力测试 |

**强制性的性能实现约束**（这些是硬性条款，编码时必须遵守）：

| 编号 | 约束 | 理由 |
|---|---|---|
| NFR-P6 | **动画只允许使用 `transform` 与 `opacity`** | 这两个属性可提升到 GPU 合成层，不触发重排重绘 |
| NFR-P7 | 禁止对大面积元素动画化 `box-shadow` / `border-radius` / `filter: blur()` | 这些都是 CPU 密集的重绘操作，4K 下会直接掉帧 |
| NFR-P8 | 需要动画的元素必须显式设置 `will-change: transform`，**动画结束后移除** | 过度使用会创建过多合成层反而变慢 |
| NFR-P9 | 3D 翻转必须使用 `transform: rotateY()` + `backface-visibility: hidden` | 保证走 GPU 合成路径 |
| NFR-P10 | 单帧并发动画元素 **≤ 8 个**；5 张牌同时滑出时需做性能实测 | 控制单帧合成压力 |
| NFR-P11 | 粒子/光效数量单次 **≤ 60 个**，且必须使用 CSS 动画而非 JS 逐帧计算 | 避免主线程阻塞 |
| NFR-P12 | 背景使用**纯 CSS 渐变或静态图片**，禁止大面积实时滤镜/模糊 | 大面积实时滤镜在核显上是灾难 |
| NFR-P13 | 必须在 **2560×1440（默认）** 与 **4K 全屏最大化**两种尺寸下分别实测帧率 | 窗口形态为"普通窗口"，但用户可能最大化 |
| NFR-P14 | 卡牌背面的 `backface-visibility` 与半透明叠加层需控制层数，避免重叠区填充率翻倍 | 卡牌翻转是填充率敏感场景 |

## 9. 技术栈选型

### 9.1 候选方案对比

| 维度 | **方案 A：Python + PyWebview(WebView2)** | 方案 B：PySide6 + QML | 方案 C：Electron + Python 后端 | 方案 D：Tkinter / PySimpleGUI |
|---|---|---|---|---|
| 技术组合 | Python 逻辑 + HTML/CSS/JS 界面，JS Bridge 通信 | Python + QML 描述式 UI | Node/Chromium 渲染 + Python 经 IPC 供数据 | 纯 Python 原生控件 |
| 4K 动画性能 | ⭐ 最佳。Chromium 合成器，`transform` 直接走 GPU 合成层 | 好，但依赖核显驱动质量，高 DPI 下易撕裂/模糊 | 好（同为 Chromium），但启动与内存代价大 | ❌ 无法实现 3D 翻转，4K 高 DPI 支持差 |
| 单文件 exe 体积 | **约 25–40MB** | 约 80–150MB | 150MB+ | ~15MB |
| 启动速度 | 1–2 秒 | 2–3 秒 | 3–5 秒 | < 1 秒 |
| Windows 触摸 | Chromium 原生 Pointer Events，成熟 | Qt 原生触摸，成熟 | 成熟 | 一般 |
| 用户实现难度 | 中（零 Web 基础，但 HTML/CSS 是 AI 生成质量最高的领域） | 中高（QML 是全新语言，改界面要写代码） | 高（两套代码需同步维护） | 低，但做不出需求效果 |
| AI 生成/修改友好度 | ⭐ 极高 | 中 | 高但维护成本高 | 高 |
| 推荐度 | **★★★★★ 已选** | ★★★☆☆ | ★★☆☆☆ | 已排除 |

> 体积估算说明：因已确认**仅支持 CSV**（TBD-04），移除了 `openpyxl` 依赖，单文件体积预计可再减少约 5–8MB。

### 9.2 选型结论与理由

**采用方案 A：Python + Pywebview（WebView2 后端）+ 原生 HTML/CSS/JS**

理由：

1. **性能层面**：在最硬的约束（4K + 无独显 + 睿频禁用）下，Chromium 的合成器架构对 `transform` / `opacity` 动画的处理最成熟——这两个属性被提升为独立合成层后，动画由 GPU 合成器直接处理，几乎不消耗主线程。这是卡牌滑出与 3D 翻转能在 4K 下流畅的**结构性保障**，而非依赖调优。
2. **体积层面**：PyWebview 不打包浏览器，复用系统 WebView2 运行时，单文件 exe 可控制在 25–40MB，远优于 Electron 的 150MB+。
3. **协作层面**：HTML/CSS 是 AI 生成质量最高、迭代最快的领域。用户在微调阶段"改配色、挪位置"只需自然语言描述，无需学习新语言。
4. **维护层面**：与用户 Python 技术背景天然契合，数据逻辑用 Python 写、界面用 Web 写，职责边界清晰。
5. **打包层面**：PyInstaller 对 PyWebview 支持成熟，`--onefile` 方案有大量成功案例。
6. **素材层面**：SVG 与 Web Audio API 均被 WebView2 原生支持，占位素材零依赖、零体积、矢量无损。

**已知代价与应对**：

- 需要系统 WebView2 运行时 → 启动时做检测与友好引导（NFR-C2）
- 用户对 Web 零基础 → 通过详细中文注释 + 零构建工具的原生写法降低门槛（NFR-M1、NFR-M5）

## 附录 B：打包建议（供用户手动执行）

> ⚠️ 依据 AGENTS.md 约定，**AI 不执行任何打包命令**。以下内容仅供参考。

**核心命令参考**

```bash
# 在项目根目录执行（依据 AGENTS.md 第七章，统一使用 uv）
uv sync                                          # 确保本地环境与 uv.lock 一致
uv add --dev pyinstaller                         # 打包工具作为开发依赖，不污染全局环境
uv run pyinstaller --onefile --windowed --name StellarDraw ^
  --paths src ^
  --add-data "src/stellardraw/ui;stellardraw/ui" ^
  --icon "src/stellardraw/ui/assets/img/app.ico" ^
  main.py
```

**关键要点**

1. **路径解析**：所有资源引用必须通过 `paths.py` 中的统一函数获取，内部判断 `getattr(sys, '_MEIPASS', ...)`，否则打包后 SVG 与前端文件会加载失败。
2. **`--windowed`**：隐藏控制台黑窗。
3. **`--add-data`**：Windows 下用 `;` 分隔源路径与目标路径（Linux/macOS 用 `:`）。
4. **图标格式**：PyInstaller 的 `--icon` 需要 `.ico` 格式。v1.1 提供的 `app_icon.svg` 需先用在线工具或 `pillow` 转换为多尺寸 `.ico`。
5. **体积优化**：在虚拟环境中打包，可通过 `--exclude-module` 排除未使用的重型模块（如 `tkinter`、`unittest`）。
6. **先 `--onedir` 调试**：单文件模式排查问题困难，建议先用目录模式验证资源加载，再切 `--onefile`。
7. **杀毒误报**：PyInstaller 产物常见误报，可向杀毒软件提交白名单，或考虑代码签名。
8. **验证环境**：务必在一台**未安装 Python** 的干净机器上双击验证（对应 AC-20）。
9. **依赖来源**：打包所用的 PyInstaller 应由 `uv add --dev pyinstaller` 加入开发依赖，避免污染全局环境（对应 NFR-D3）。
10. **`--paths src` 必不可少**：根目录 `main.py` 是在**运行时**把 `src/` 注入 `sys.path` 后才 import `stellardraw` 的，而 PyInstaller 做的是**静态分析**、不会执行这段注入代码。若不显式给出 `--paths src`，打包后会报 `ModuleNotFoundError: No module named 'stellardraw'`。
11. **两类路径必须分开**：静态资源（`ui/` 下的 HTML/CSS/JS/SVG）打包后位于 `_MEIPASS` 临时解包目录，须用 `sys._MEIPASS` 读取；而运行时数据（`data/` 下的名单与配置）必须写到 **exe 所在目录**（`Path(sys.executable).parent`）——**绝不能写进 `_MEIPASS`**，那是临时目录，软件一关数据就丢了。这正是 `paths.py` 需要提供**两个**路径函数的原因。
